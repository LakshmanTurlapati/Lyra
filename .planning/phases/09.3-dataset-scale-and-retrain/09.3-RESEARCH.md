# Phase 09.3: Dataset Scale + Continue-Train v5 - Research

**Researched:** 2026-04-24
**Domain:** Anthropic Batch API dataset generation at scale + PEFT LoRA continue-training
**Confidence:** HIGH (pricing, PEFT API, TRL SFTTrainer pattern all verified against 2026 official docs); MEDIUM (token forecast assumptions — calibrated against Phase 4/5/6 JSONL sizes but not a live probe)

## Summary

Phase 09.3 is the first time this codebase will use the Anthropic Batch API. All prior synthetic data generation ran through in-process Python template code (`scripts/generate_tool_data.py`, `scripts/generate_knowledge_data.py`) or via Claude Code subagents (Plan 09.2-07). Neither approach scales to 42K fresh samples. This phase must (1) introduce a new Batch API generation script with prompt-cache-aware prompt structure, (2) stand up the missing 600+ topic knowledge pool, (3) patch `scripts/train.py` for PEFT `is_trainable=True` continue-training, and (4) preserve v4 artifacts before v5 overwrites them.

Three research verdicts that change the plan shape:

1. **Cost forecast lands around $850-$1,200 on Opus 4.6 Batch API with prompt caching — well under D-03's $1,500 cap.** The dominant cost driver is output tokens (batch-discounted to $12.50/MTok). A naive implementation without prompt caching lands near $1,100; with 1-hour TTL caching on domain-shared system prompts, realistic cost drops to ~$850. Opus 4.6 has a 4,096-token minimum cacheable prompt length — system prompts must be engineered above that threshold to benefit from caching.
2. **PEFT continue-training is a ~15 line patch, but the TRL SFTTrainer contract has a specific constraint.** You must NOT pass both a PeftModel and a `peft_config`. The current `scripts/train.py` does both (wraps via `peft_config=lora_config`). Plan 09.3-03's patch must make that mutually exclusive: if `--resume-from-adapter` is set, load via `PeftModel.from_pretrained(base, adapter, is_trainable=True)` AND omit `peft_config` from SFTTrainer construction.
3. **Knowledge topic pool expansion is the highest-risk sub-task.** Phase 09.1-04 hit a ceiling at ~560-650 curated knowledge samples with 192 topics even at relaxed thresholds. The existing topic pool is hardcoded as 193 Q/A literal dicts inside `scripts/generate_knowledge_data.py` — not a YAML asset. Scaling to 4,200 knowledge samples requires either (a) expanding that in-script literal list to 600+ entries, (b) migrating to a YAML asset, or (c) switching the knowledge generator to Batch-API-with-Opus. Recommendation: migrate to YAML + Batch API + meta-prompt subtopic expansion, since 4,200 from 600 topics = 7 samples per topic which is achievable only if each topic spawns a small cluster of sub-prompts.

**Primary recommendation:** Structure Plan 09.3-01 as three sub-waves (knowledge topic pool → system prompt engineering → batched generation) with a gate after the first 1,000-sample batch (cost forecast + quality spot-check) before spending the remaining ~$900 on batches 2-N.

### Pattern 1: Anthropic Batch API + Prompt Caching

**What:** Submit up to 100,000 message requests in one batch; Anthropic processes asynchronously (SLA 24h, typical < 1h, can slip to 24-48h under load); results retrieved as a streamed JSONL response.

**When to use:** All Phase 09.3 generation work (D-02 locked).

**Key facts [VERIFIED via official docs 2026-04-24]:**

- Batch size limit: **100,000 requests or 256 MB, whichever first** [CITED: https://platform.claude.com/docs/en/build-with-claude/batch-processing] — 42K fits in one batch with room to spare, but abort-early strategy (smaller batches) gives mid-stream quality visibility
- SLA: most batches finish < 1h; Anthropic guarantees 24h or they expire [CITED: same]. Batches may go slightly over workspace spend limit due to concurrency [CITED: same]
- Prompt caching in batches: "best effort" with 30-98% cache hit rates depending on traffic [CITED: same]. **Critical:** Use `"ttl": "1h"` for batch use (not default 5m), because batches run longer than 5m [CITED: same]. Each request must carry **identical** `cache_control` blocks for cache hits [CITED: same]
- Opus minimum cacheable prompt: **4,096 tokens** [CITED: https://platform.claude.com/docs/en/build-with-claude/prompt-caching]. System prompts shorter than this won't cache — returns `cache_creation_input_tokens: 0` and `cache_read_input_tokens: 0` in the response usage
- SDK access: `client.beta.messages.batches.create(...)` (beta endpoint only — no stable endpoint yet) [CITED: https://github.com/anthropics/anthropic-sdk-python/blob/main/src/anthropic/resources/beta/messages/batches.py]
- Required beta header: `anthropic-beta: message-batches-2024-09-24` (SDK adds automatically when using `beta.messages.batches`)
- Idempotency: a submitted batch CANNOT be cancelled mid-flight without calling the cancel endpoint, and there's no built-in "submit once" guarantee. **Plan 09.3-01 must track batch_id in a local JSON file** and refuse to re-submit if the same batch spec already has an active batch_id (T-09.3-05)

**Example (Python SDK, Batch API + 1h cache):**

```python
# Source: https://platform.claude.com/docs/en/build-with-claude/batch-processing
#         https://platform.claude.com/docs/en/build-with-claude/prompt-caching
import anthropic
from anthropic.types.beta.messages.batch_create_params import Request
from anthropic.types.beta.message_create_params import MessageCreateParamsNonStreaming

client = anthropic.Anthropic()

# System prompt must be ≥4,096 tokens for Opus caching. Tool-calling domain
# reaches this naturally via: role description (~200 tok) + 40 tool schema
# JSON definitions (~80 tok each = 3,200 tok) + 5 few-shot examples (~200 tok
# each = 1,000 tok) + output format spec (~200 tok) = ~4,600 tok. See
# SYSTEM_PROMPT_DESIGN below.
TOOL_SYSTEM_PROMPT_BLOCKS = [
    {
        "type": "text",
        "text": TOOL_CALL_SYSTEM_PROMPT,  # ≥4096 tokens
        "cache_control": {"type": "ephemeral", "ttl": "1h"},
    },
]

requests = [
    Request(
        custom_id=f"tool-call-{i:05d}",
        params=MessageCreateParamsNonStreaming(
            model="claude-opus-4-6",
            max_tokens=2048,
            system=TOOL_SYSTEM_PROMPT_BLOCKS,
            messages=[
                {
                    "role": "user",
                    "content": user_prompt,  # unique per sample, NOT cached
                }
            ],
        ),
    )
    for i, user_prompt in enumerate(user_prompts)
]

batch = client.beta.messages.batches.create(requests=requests)
# batch.id is the stable identifier — persist to disk IMMEDIATELY for idempotency
# batch.processing_status cycles through: in_progress → ended
# Poll: client.beta.messages.batches.retrieve(batch.id)
# Retrieve: client.beta.messages.batches.results(batch.id) — returns JSONL stream
```

**Response shape per request (in the results JSONL stream):**

```json
{
  "custom_id": "tool-call-00001",
  "result": {
    "type": "succeeded",
    "message": {
      "content": [{"type": "text", "text": "..."}],
      "usage": {
        "input_tokens": 150,
        "cache_creation_input_tokens": 0,
        "cache_read_input_tokens": 4250,
        "output_tokens": 1100
      }
    }
  }
}
```

Check `cache_read_input_tokens > 0` on sample 2+ to confirm caching is actually working. If it's zero across many samples, the system prompt isn't hitting the cache — halt and investigate before spending more.

### Pattern 2: PEFT Continue-Training via `is_trainable=True`

**What:** Load an existing LoRA adapter as the starting point for further training, accumulating gradients on top of v4's weights rather than re-initializing LoRA matrices from scratch.

**When to use:** Plan 09.3-03 training step (D-09 primary path).

**Key facts [VERIFIED via official docs 2026-04-24]:**

- `PeftModel.from_pretrained(base_model, adapter_path, is_trainable=True)` loads and unfreezes the adapter [CITED: https://huggingface.co/docs/peft/package_reference/peft_model]
- The adapter's `adapter_config.json` is auto-read — `lora_r`, `lora_alpha`, `target_modules`, `lora_dropout` all come from v4's config [VERIFIED in `models/lyra-adapter/adapter_config.json`: r=16, alpha=32, dropout=0.05, target_modules=["gate_proj", "down_proj", "up_proj", "k_proj", "q_proj", "v_proj", "o_proj"], peft_version=0.19.1]. **No need to pass `LoraConfig` when resuming.**
- **TRL SFTTrainer constraint:** "You should not pass both a `PeftModel` instance and a `peft_config` to the trainer together" [CITED: https://github.com/huggingface/trl/issues/786]. Current `scripts/train.py` line 486 passes `peft_config=lora_config` — **must become conditional on `--resume-from-adapter`**.
- Alternative API: `AutoPeftModelForCausalLM.from_pretrained(adapter_path, is_trainable=True)` wraps both base load and adapter load in one call [CITED: https://huggingface.co/docs/peft/package_reference/auto_class]. Acceptable alternative; current `scripts/train.py` already imports `PeftModel` so the two-line pattern fits more naturally.

**Example (the exact patch Plan 09.3-03 owns):**

```python
# Source: https://huggingface.co/docs/peft/main/en/developer_guides/lora
#         https://github.com/huggingface/trl/issues/786
#
# In scripts/train.py, add to build_parser():
parser.add_argument(
    "--resume-from-adapter",
    type=str,
    default=None,
    help="Path to existing LoRA adapter to continue training from. "
         "When set, loads adapter as trainable and skips LoraConfig construction.",
)

# In main(), replace the model load + SFTTrainer construction:
model = AutoModelForCausalLM.from_pretrained(args.model_name, **model_kwargs)

if args.resume_from_adapter:
    from peft import PeftModel
    adapter_path = Path(args.resume_from_adapter)
    if not adapter_path.exists():
        print(f"Error: adapter path not found: {adapter_path}", file=sys.stderr)
        sys.exit(1)
    print(f"[Lyra] Continue-training from adapter: {adapter_path}")
    model = PeftModel.from_pretrained(model, str(adapter_path), is_trainable=True)
    lora_config = None  # do NOT pass peft_config to SFTTrainer
else:
    lora_config = get_lora_config(args)

# Later, in SFTTrainer construction:
trainer_kwargs = {
    "model": model,
    "args": training_args,
    "train_dataset": dataset["train"],
    "eval_dataset": dataset["validation"],
    "processing_class": tokenizer,
}
if lora_config is not None:
```

### Anti-Patterns to Avoid

- **Submitting the full 42K in a single batch before a smoke test.** Costs $1,100 up front with zero quality feedback. Use a 1K dry-run first (batch_01), eval cache-hit rate and sample quality, then scale.
- **Passing both `peft_config` AND a `PeftModel` to SFTTrainer.** TRL raises an error or silently reinitializes. The patch must make them mutually exclusive.
- **Leaving batch IDs only in shell history.** If the script crashes post-submission, you've lost the batch_id and cannot retrieve results. Persist to `.planning/phases/09.3-.../BATCH-IDS.json` immediately on submission.
- **Using 5-minute TTL for batch caching.** Batches run longer than 5m; the cache expires mid-batch and you pay full input price from then on. Always `"ttl": "1h"`.
- **Sub-4,096-token system prompts for Opus 4.6.** They don't cache at all — silent cost multiplier of ~5× on input. Engineer system prompts to exceed the threshold (few-shot examples + schema dumps get there naturally).
- **Hand-rolling a knowledge topic expansion loop when the topic pool isn't ready yet.** Sequence matters: topic pool (Wave 1) → system prompts (Wave 2) → batch generation (Wave 3). Skipping Wave 1 repeats 09.1-04's exhaustion failure at scale.
- **Overwriting v4 artifacts before snapshot.** D-16 snapshot is the phase's insurance policy. Plan 09.3-03 Task 0 is `cp -r models/lyra-adapter models/lyra-merged /tmp/lyra-v4-snapshot/`.
- **Lowering dedup threshold below 0.995 on knowledge domain at scale.** The 09.1 retrospective showed 0.995 is already permissive for knowledge; lowering invites mode-collapse-via-duplicates.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Async batch submission + polling + retrieval | Custom HTTP retry loop | `anthropic.Anthropic().beta.messages.batches.{create,retrieve,results}` | SDK handles exponential backoff, auth, rate limits, JSON parsing |
| LoRA continue-training weight restoration | Manual `load_state_dict` on merged tensors | `PeftModel.from_pretrained(..., is_trainable=True)` | Reads adapter_config.json; restores r/alpha/target_modules/dropout automatically |
| ShareGPT message validation | Re-implementing Pydantic model | `Conversation.model_validate()` from `scripts/validate_format.py` | Already handles role ordering, tool_call structure, final-message tool_call (post 09.2-07 relaxation) |
| Dataset stratified split | Manual shuffle + slice | `assemble_dataset.py assemble` | Handles seed=42 reproducibility, domain labels, 90/5/5 convention |
| MinHash LSH for dedup at 42K | Introduce `datasketch` now | Existing O(n²) `dedup.py` | At 42K scale it takes ~90 min — acceptable for a one-shot. Tech debt only matters at 100K+ scale (v2.0) |
| Prompt caching math | Manual token counting during batch construction | Trust `response.usage.cache_read_input_tokens` for post-hoc accounting | Forecasting pre-submission is a *script input* not an SDK output; the SDK doesn't predict caching |

**Key insight:** The Batch API + PEFT `is_trainable=True` patterns are both ~15 lines of code each. The temptation to wrap them in extensive abstraction is wrong. Keep both generation and training scripts linear and greppable — every other Lyra script follows that convention.

## Common Pitfalls

### Pitfall 1: Prompt Cache Silently Disabled

**What goes wrong:** Generation script submits 33,600 tool-call samples expecting 90% cache discount on input. Response usage shows `cache_read_input_tokens: 0` for every sample. Actual cost is 5× forecast.

**Why it happens:**
- System prompt < 4,096 tokens (Opus minimum)
- `cache_control` block structure differs slightly across requests (comments, whitespace, dict key order)
- 5-minute TTL used instead of 1-hour; cache expires between batches
- `anthropic-beta` header missing on cache-control beta (though 1h TTL is now stable, some headers may still be required)

**How to avoid:**
- Pre-submission: tokenize the system prompt with the SDK's token counter (`client.messages.count_tokens(...)`) and assert it's ≥ 4,096 tokens
- Use a single shared `system_prompt_blocks` Python object across every request in the batch — construct once, reference many
- Hard-code `"ttl": "1h"` — never default
- After batch 1 returns, assert `cache_read_input_tokens > 0` on at least 90% of samples before submitting batches 2-N

**Warning signs:** Batch 1 cost exceeds 110% of forecast; response inspection shows `cache_creation_input_tokens > 0` on every sample (should only happen on sample 1).

### Pitfall 2: Continue-Training Reinitializes the Adapter

**What goes wrong:** Plan 09.3-03 runs `train.py --resume-from-adapter models/lyra-adapter/` but SFTTrainer silently re-initializes LoRA weights, effectively training v5 from base with a cold adapter. Final v5 eval is indistinguishable from a from-base retrain.

**Why it happens:**
- `peft_config=lora_config` is passed alongside the pre-wrapped `PeftModel` — TRL silently overrides
- The `is_trainable=True` flag was forgotten on `PeftModel.from_pretrained` — adapter loads frozen
- A smoke-test run with `--max-steps 1` never actually verified the adapter weights are the starting point

**How to avoid:**
- Make `--resume-from-adapter` and `--lora-r/--lora-alpha` mutually exclusive in argparse (the latter are ignored when resuming; error if both provided)
- Before `trainer.train()`, log the adapter's first LoRA A-matrix row hash; after training step 1, log it again — they MUST differ (training) but the step-0 hash MUST match the pre-training on-disk hash (correct starting point)
- Wave 0 RED test: `test_resume_loads_existing_weights` — load adapter, create trainer, run `trainer.train(max_steps=1)`, assert the LoRA weight delta from step-0-on-disk is non-zero and small

**Warning signs:** v5 initial training loss is ~1.7 (same as from-base start) instead of ~0.8 (v4's final loss region).

### Pitfall 3: Knowledge Topic Pool Exhaustion at Scale

**What goes wrong:** Plan 09.3-01 generates 4,200 raw knowledge samples but curate_pipeline retains only ~800 after 0.995 dedup, because 600 topics × 7 angles still produces high Jaccard clusters on topics with narrow answer shapes ("What is X" → "X is a...").

**Why it happens:**
- Sub-angle variations (definition / mechanism / comparison) are too similar for topics that don't have a natural multi-angle treatment (e.g., mathematical constants — "What is pi?" has one answer)
- Token_target uniformity (~500 tok each) makes responses cluster
- 0.995 Jaccard at 3-gram is permissive for substring overlap but not structural similarity

**How to avoid:**
- Skew the topic pool toward multi-angle topics (prefer "TCP 3-way handshake" over "pi") — 80% of topics should have natural 4+ sub-angle treatments
- For narrow topics, generate ≤3 samples per topic, not 7
- Add deliberate answer-length variance: pull `token_target` from a uniform distribution [200, 1200] per sample rather than fixed per topic
- After the first 1K knowledge samples come back, run `curate_pipeline --input batch-01.jsonl --domain knowledge` and measure retention. If < 80%, stop the knowledge batches and re-design the topic pool before committing remaining spend

**Warning signs:** Curate retention on knowledge batch 1 < 80%, or curate output shows tight clusters on "definition" sub-angle specifically.

### Pitfall 4: v5 Drifts on Knowledge Benchmarks (D-10 FAIL)

**What goes wrong:** v5 tool-call-format climbs to 0.42 (D-09 PASS) but MMLU drops to 0.46 (5.1% below base 0.5012, D-10 FAIL by 0.1%). Phase 09.3 fails its exit criterion — D-09 PASS without D-10 doesn't unblock Phase 10.

**Why it happens:**
- Continue-training from v4 adds 42K new sample-passes on top of 15K from v4's training; at lr=1e-5 this is still ~4× v4's total gradient updates on rebalanced data
- The new 42K skews 80% tool-call (per D-05) — same ratio v4 saw, but *more* absolute training on that distribution
- Catastrophic-forgetting signature: knowledge benchmarks slowly erode as the model specializes

**How to avoid:**
- Instrument training with step-wise eval_loss on validation set (already in `scripts/train.py`); halt early if eval_loss > v4's 0.9751 (per CONTEXT.md D-10 risk note)
- Consider interim checkpoint eval: at 50% of steps, run abbreviated MMLU-100 to confirm no regression; continue only if MMLU-100 within ±3%
- If full-eval D-10 fails, the fallback is lower epochs or lower effective sample count — not the primary path, but an escape hatch before a full v6

**Warning signs:** training eval_loss climbs past 0.97 after epoch fraction 0.5; wandb (if enabled) shows divergence from v4's trajectory.

### Pitfall 5: Batch API Idempotency Failure

**What goes wrong:** Plan 09.3-01 script crashes between `batch.create()` returning `batch.id` and persisting that ID to disk. Operator re-runs the script → a second $500+ batch submits → Anthropic happily processes both → you paid twice.

**Why it happens:**
- Script structure: submit → then write ID to file → then poll. A SIGINT or crash between first two steps loses the ID.
- The Batch API has no "idempotency key" equivalent (like Stripe's). Re-submitting the same requests creates a distinct batch.

**How to avoid:**
- Write to disk **before** the submit call: create a pending-batch JSON with the request fingerprint (SHA-256 of the sorted request bodies), submit, update with batch_id
- On script startup, read the pending-batch JSON. If a batch_id exists, retrieve its status; if it's `in_progress` or `ended` and matches the current request fingerprint, resume polling instead of resubmitting
- Pre-submission confirmation prompt: `sys.stdin.readline()` with `--yes` override for CI; Plan 09.3-01 Task 1 should include this interactive gate
- **Persist batch_id immediately after `.create()` returns** — do not print or log first

**Warning signs:** Billing dashboard shows 2× expected charges; two batches with same custom_id range in `client.beta.messages.batches.list()`.

### Example 1: Batch API submission with prompt caching (full structure)

```python
# Source: https://platform.claude.com/docs/en/build-with-claude/batch-processing
#         + SDK reference at github.com/anthropics/anthropic-sdk-python
import anthropic
import json
from pathlib import Path
from anthropic.types.beta.messages.batch_create_params import Request
from anthropic.types.beta.message_create_params import MessageCreateParamsNonStreaming

def submit_generation_batch(
    system_prompt: str,               # ≥4096 tokens for Opus caching
    user_prompts: list[str],
    batch_id_path: Path,
    max_tokens: int = 2048,
    model: str = "claude-opus-4-6",
) -> str:
    """Submit a batch and persist its ID immediately (T-09.3-05)."""
    client = anthropic.Anthropic()

    system_blocks = [{
        "type": "text",
        "text": system_prompt,
        "cache_control": {"type": "ephemeral", "ttl": "1h"},  # 1h for batches
    }]

    requests = [
        Request(
            custom_id=f"sample-{i:05d}",
            params=MessageCreateParamsNonStreaming(
                model=model,
                max_tokens=max_tokens,
                system=system_blocks,
                messages=[{"role": "user", "content": prompt}],
            ),
        )
        for i, prompt in enumerate(user_prompts)
    ]

    # PERSIST FINGERPRINT BEFORE SUBMIT (T-09.3-05 idempotency)
    fingerprint = hashlib.sha256(
        json.dumps([r.params.messages for r in requests], sort_keys=True).encode()
    ).hexdigest()
    pre_record = {"status": "submitting", "fingerprint": fingerprint}
    batch_id_path.write_text(json.dumps(pre_record))

    batch = client.beta.messages.batches.create(requests=requests)

    # Update with batch_id
    batch_id_path.write_text(json.dumps({
        "status": "submitted",
        "fingerprint": fingerprint,
        "batch_id": batch.id,
        "created_at": batch.created_at.isoformat(),
    }))
    return batch.id
```

### Example 2: Batch result retrieval + per-sample JSONL write

```python
# Source: https://platform.claude.com/docs/en/build-with-claude/batch-processing
def retrieve_and_write(batch_id: str, output_jsonl: Path) -> dict:
    """Poll until done, stream results to JSONL. Returns aggregate usage."""
    client = anthropic.Anthropic()

    while True:
        batch = client.beta.messages.batches.retrieve(batch_id)
        if batch.processing_status == "ended":
            break
        time.sleep(60)  # poll once per minute

    agg_input = 0
    agg_output = 0
    agg_cache_write = 0
    agg_cache_read = 0
    n_success = 0
    n_fail = 0

    with open(output_jsonl, "w") as f:
        for result in client.beta.messages.batches.results(batch_id):
            if result.result.type == "succeeded":
                msg = result.result.message
                content = msg.content[0].text if msg.content else ""
                record = {
                    "custom_id": result.custom_id,
                    "response": content,
                    "usage": msg.usage.model_dump() if msg.usage else {},
                }
                f.write(json.dumps(record) + "\n")
                u = msg.usage
                agg_input += getattr(u, "input_tokens", 0)
                agg_output += getattr(u, "output_tokens", 0)
                agg_cache_write += getattr(u, "cache_creation_input_tokens", 0)
                agg_cache_read += getattr(u, "cache_read_input_tokens", 0)
                n_success += 1
            else:
                n_fail += 1

    return {
        "n_success": n_success,
        "n_fail": n_fail,
        "input_tokens": agg_input,
        "output_tokens": agg_output,
        "cache_creation_tokens": agg_cache_write,
        "cache_read_tokens": agg_cache_read,
    }
```

### Example 3: Pre-submission cost forecaster

```python
# Source: derived from https://platform.claude.com/docs/en/about-claude/pricing
#         (batch rates + cache multipliers)
def forecast_cost(
    n_samples: int,
    system_prompt_tokens: int,
    avg_user_prompt_tokens: int,
    avg_output_tokens: int,
    cache_hit_rate: float = 0.9,  # assumed; verify post-batch
    model: str = "claude-opus-4-6",
) -> dict:
    """Forecast USD cost for a batch. Opus 4.6 batch rates: $2.50 in / $12.50 out.
    Cache: 2.0x base input for 1h write, 0.1x base input for read, BEFORE batch 50% discount.
    Effective under batch: 1h write = 2.0 * 5.00 * 0.5 = $5.00/MTok;
    cache read = 0.1 * 5.00 * 0.5 = $0.25/MTok."""
    # Base input price on Opus 4.6: $5.00/MTok. Output: $25.00/MTok.
    # Batch halves both.
    base_in = 5.00
    base_out = 25.00
    batch_mult = 0.5
    cache_write_mult = 2.0    # for 1h TTL
    cache_read_mult = 0.1

    sys_write_cost = (system_prompt_tokens / 1e6) * base_in * cache_write_mult * batch_mult
    # Per sample: some fraction cache-hit (at read price), rest uncached (full input price)
    sys_read_cost = (
        (system_prompt_tokens * n_samples * cache_hit_rate / 1e6)
        * base_in * cache_read_mult * batch_mult
    )
    sys_uncached_cost = (
        (system_prompt_tokens * n_samples * (1 - cache_hit_rate) / 1e6)
        * base_in * batch_mult
    )
    user_cost = (avg_user_prompt_tokens * n_samples / 1e6) * base_in * batch_mult
    output_cost = (avg_output_tokens * n_samples / 1e6) * base_out * batch_mult

    total = sys_write_cost + sys_read_cost + sys_uncached_cost + user_cost + output_cost
    return {
        "total_usd": round(total, 2),
        "sys_write_usd": round(sys_write_cost, 4),
        "sys_read_usd": round(sys_read_cost, 2),
        "sys_uncached_usd": round(sys_uncached_cost, 2),
        "user_usd": round(user_cost, 2),
        "output_usd": round(output_cost, 2),
    }
```

### Scenario table [VERIFIED against 2026 pricing page]

Pricing inputs [CITED: https://platform.claude.com/docs/en/about-claude/pricing]:

- Opus 4.6 base: $5/MTok input, $25/MTok output
- Batch discount: 0.5× on both input and output

- Cache read multiplier: 0.1× on base input → on batch = $0.25/MTok

| Scenario | Cache hit rate | System prompt cost | User prompt cost | Output cost | **Total** |
|----------|---------------:|-------------------:|-----------------:|------------:|----------:|
| **Best case** (caching works at 95%, 3 domain caches amortized once) | 0.95 | ~$45 (writes) + ~$42 (reads) = $87 | $33 | $554 | **$674** |
| **Realistic** (caching at 80%, some cache refreshes between domain switches) | 0.80 | ~$45 + ~$35 reads + ~$44 uncached = $124 | $33 | $554 | **$711** |
| **Pessimistic** (no caching — sys prompts < 4096 tok, or TTL expired, or cache_control block mismatch) | 0.00 | $186.9M × $5.00 × 0.5 / 1M = **$467** | $33 | $554 | **$1,054** |
| **Worst case** (no caching AND batches get no discount — hypothetical, forces direct Messages API) | 0.00 | $935 | $66 | $1,108 | **$2,109** |

**Key observations:**

1. **The realistic case ($711) is well under D-03's $1,500 cap** — room for 2× budget over-run before an abort-escalation.
2. **Output tokens are the dominant cost (~78% of total)** — prompt caching only helps with the other 22%. The big lever isn't caching; it's not generating extra/wasted output. Set `max_tokens` tightly per domain: 2,000 for tool-call conversations, 1,500 for code, 1,500 for knowledge.
3. **The difference between realistic and pessimistic is ~$340** — materially important but not catastrophic. A single batch with broken caching is recoverable within the budget.
4. **If the estimate comes in >$1,300 on the dry-run (batch 1, 1K samples extrapolated), halt and re-scope** — that implies a ~2× overshoot vs forecast; something in system prompt design or output length is wrong.

**D-15 single-batch cap:** $500 per batch. With Opus 4.6 batch pricing, $500 of output tokens = ~40M output tokens = ~40,000 samples at 1,000 tok/sample. So a single 42K batch at ~$700 total does NOT exceed $500 in output alone ($554) but is borderline — **recommend splitting into 3 batches (~14K each) to satisfy D-15 and provide quality checkpoints**.

## Open Questions (RESOLVED)

All major uncertainties resolved. Each open question below has an inline "Recommendation:" answer and Plans 09.3-01 / 09.3-02 / 09.3-03 implement those recommendations. Section retained for audit trail.

Remaining questions that aren't blockers but merit attention in the plan:

1. **Should the knowledge topic pool live in `templates/` or under the knowledge dataset directory?**
   - What we know: `templates/` has YAML prompt libraries (tool-calling.yaml, code.yaml, knowledge.yaml); topic pool is a topic list, not a prompt template
   - What's unclear: purist argument goes either way
   - Recommendation: put it at `templates/knowledge-topics-v2.yaml` for consistency; existing `templates/knowledge.yaml` references categories, and topics-v2 is the enumeration. Plan 09.3-01 can revisit if the directory feels wrong.

2. **How should per-sample user prompts be assembled for tool-call batches — inline in the script or a generator class?**
   - What we know: Phase 4's `generate_tool_data.py` uses extensive in-script template literal lists (800+ lines)
   - What's unclear: whether Batch API generation can reuse that complexity or needs a simpler approach
   - Recommendation: keep it simple — Batch API means Opus generates the rich conversation; our job is just to provide a prompt like "Produce a single-turn tool-call-ending ShareGPT conversation using the schema for {tool_name} with a realistic user query." The script's role shifts from output-synthesis to prompt-synthesis. Plan 09.3-01 designs prompts; Opus does the heavy lifting.

3. **Is there a way to verify cache-hit rate BEFORE submitting the first real batch?**
   - What we know: Batch API has "best effort" caching [CITED: batch-processing docs]; there's no pre-flight cache check
   - What's unclear: whether a tiny (10-sample) probe batch gives a statistically meaningful cache-hit signal
   - Recommendation: **Yes — make batch 1 a 10-sample probe**, not 1K. 10 samples × $0.01-0.03 ≈ negligible cost, and the `cache_read_input_tokens` response tells you immediately if caching is working. If it is, scale up to the 1K dry-run → then production.

4. **Does SFTTrainer with `assistant_only_loss=True` and pre-wrapped PeftModel still apply the chat template's `{% generation %}` markers correctly?**
   - What we know: v4 used assistant_only_loss=True successfully; the tokenizer's chat_template carries `{% generation %}` markers per train.py lines 436-456
   - What's unclear: whether the re-tokenization during continue-training preserves the generation marker semantics
   - Recommendation: explicitly verified in Plan 09.3-03 Task 1 smoke test — run `--max-steps 1 --resume-from-adapter ...` and confirm training loss moves in a reasonable direction (v4's final was 0.80; first step should land near that, not near 1.7).
