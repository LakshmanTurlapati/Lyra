## Executive Summary

**Root cause: H1 — training-distribution mode collapse.** The v2 retrain memorized a narrow pool of canned text suffixes and over-indexed on tool-calling content, producing a model that reflex-emits one of five canned "I've completed the task..." templates in place of tool calls and, when it does emit a tool call, collapses onto two memorized outputs (`get_weather(city="Tokyo")`, `git_commit(message="Fix typo in docs")`) regardless of user intent. The evidence is airtight on both the downstream behavioral signature (Plan 03) and the source-side training distribution (Plan 04), with alternative causes (template persistence H5, eval drift H3, merge-time numerics H4) ruled out or substantially weakened.

**Three corrective actions are available.** None is obviously dominant: 06A (retrain v3) can in principle clear D-09 but at a 3.5 h wall-clock cost and with a real risk of re-collapsing; 06B (targeted patch) cannot manufacture tool-call endings that never appeared in training; 06C (ship base as v1.0) is the lowest-risk exit but **does not itself satisfy the D-09 `tool-call-format > 0.41` bar against the current post-9bec343 test split (base measures 0.3422)**. The recommendation below picks 06A with explicit contingencies because it is the only branch that can actually clear D-09 — but the probability of success is not high, and the user should enter this branch with eyes open to a potential fall-back to 06C.

### Cross-Evidence Causal Chain

1. **Training** (D-06): 0% of tool-calling samples end in `<tool_call>`; 46% end in one of 5 canned text suffixes.
2. **→ Learned behavior**: model learns "when in a tool-calling dialog, close with a canned text summary" as the dominant pattern.
3. **→ Dataset-mode inference** (D-03): on multi-turn prompts, v2 reflex-emits a canned summary (85%) instead of a tool_call.
4. **→ Single-turn inference** (D-05): with no prior tool-result context, v2 DOES emit `<tool_call>` (XML machinery intact), BUT the argument slots collapse onto the dominant training-time tool-name + memorized argument value (`get_weather` + `Tokyo`; `git_commit` + `"Fix typo in docs"`).
5. **→ Knowledge regression** (base MMLU 0.5012 → v2 0.4635 = −7.5% relative): 90.22% tool-calling domain skew means only ~5% of gradient updates ever touched non-tool-calling content — classic catastrophic forgetting signature under skew.

The training data distribution **directly predicts** the failure shape observed at inference. Every downstream symptom has a source-side number that matches.

## Root Cause

**The v2 regression is caused by H1: training-distribution mode collapse driven by two coupled pathologies in `datasets/assembled/train`:**

1. **Suffix memorization.** Every one of the 10,793 tool-calling training samples ends in assistant text (0.00% end in a `<tool_call>`), and 46.0% of them end with one of five near-duplicate canned prefixes (`"I've gathered all the information..."`, `"I've completed the task. [VAR] the operation was successful."`, etc.). The SFT optimizer found these five canned suffixes and locked onto them — eval_loss 0.1384 at epoch 2 reflects memorization of a finite phrase pool, not generalization. At inference, v2 reflex-emits one of these canned summaries in 45% of dataset-mode generations and an `[Tool result from X]:` echo in another 40%, totaling 85% response-shell dominance on multi-turn tool-calling prompts.

2. **Domain skew + catastrophic forgetting.** 90.22% of train is tool-calling; 4.90% knowledge; 4.88% code. Only ~5% of gradient updates ever touched non-tool-calling content. This directly predicts v2's −7.5% MMLU regression (0.5012 → 0.4635) and its inability to fall back to general text when the tool-calling response shells are uncalled for. When the model DOES emit a `<tool_call>` (single-turn mode, where the XML machinery is intact), it collapses onto the most-frequent training-time tool-name (`get_weather`) and argument (`Tokyo`) — 6 of 8 probe prompts collapsed this way regardless of intent.

**These two pathologies are coupled at the data-generation layer** (`scripts/gen_tool_calls.py`). The template-based generator emits conversations that always end with a short pool of canned summary phrases, and the full-scope dedup threshold (0.9) removes near-duplicates *between* conversations without removing canned endings *within* each conversation. The fix therefore lives in the training-data distribution and (secondarily) in regularization of the loss signal — NOT in the chat template (D-04 passed), the tokenizer (D-04 passed), the merge numerics (no evidence), or the eval harness (D-07 amended PASS).

Every other hypothesis is either mechanically eliminated (H5) or cannot account for the ≥85% canned-response rate and the 7/8 mode-collapse rate simultaneously (H2, H3, H4).

### Branch 06A — Retrain with rebalanced data + adjusted hyperparameters (RECOMMENDED)

**When this is the right choice:**
- H1 is the confirmed root cause (it is — posterior ~90%).
- H1 lives entirely in the training-data distribution, so retraining with a fixed distribution is the ONLY branch that can directly address the root cause.
- The user accepts one ~3.5 h retrain cycle with measurable success criteria.
- The user accepts that if v3 also fails D-09, the phase then falls back to 06C (ship base).

**Changed hypothesis for D-10 compliance:** "The v2 regression was driven by (a) 46.0% canned-suffix coverage over 5 templates and (b) 0.00% tool-call-ending tool-calling samples, combined with 90.22% tool-calling domain skew. v3 addresses all three: expand the ending-phrase pool to drive top-5 coverage below 0.20, inject ≥500 single-turn tool-call-ending samples to push `pct_end_in_tool_call` above 4%, and rebalance domains to push tool-calling skew below 0.80."

**Specific retrain menu (Plan 06A will pick exact values, with user approval):**
- **Data changes (required — the root cause fix):**
  - Expand the canned-suffix pool in `scripts/gen_tool_calls.py` generator to push top-5 60-char prefix coverage from 0.46 to ≤ 0.20. (Re-runs the xfail test to XPASS; hits the 0.50 ceiling comfortably.)
  - Add ≥500 single-turn tool-call-ending samples (assistant turn = `<tool_call>...</tool_call>` only, no trailing summary) to the tool-calling split. This directly undoes the 0.00% → target ~4% shift and gives the model a training example of "the correct answer IS a tool call, nothing after."
  - Oversample or augment code (+584) and knowledge (+586) curated splits to push tool-calling domain fraction from 0.9022 to ≤ 0.80 (ideally 0.70). CI ceiling is 0.92 so this passes comfortably.
- **Hyperparameter changes (secondary — regularization):**
  - `lr`: 1e-4 → 5e-5 (halve; mitigates memorization of the remaining canned pool — per RESEARCH.md Assumption A1, still flagged LOW confidence without empirical validation)
  - `epochs`: 2 → 1 (epoch-2 eval_loss dropped 0.0229 which was mostly deepening the memorization; 1 epoch limits that)
  - Keep `per_device_batch=4`, `grad_accum=4` unchanged (no evidence these contributed).
- **Inference-time regularization (optional, cheap belt-and-suspenders):** none required — D-04 confirms template is correct.

**Success gate (enforced by Plan 06A):** D-09 — `tool-call-format > 0.41` AND |Δ MMLU| ≤ 5% AND |Δ ARC| ≤ 5% AND |Δ HellaSwag| ≤ 5%, all against `results/base_full.json`. If v3 fails D-09, Plan 06A halts and returns to Plan 05 with the new evidence; the user may then authorize a v4 retrain (with a new hypothesis) or redirect to 06C.

**Risk:**
- 3.5 h wall-clock cost per retrain attempt (D-10 reinforces this is not free).
- **Success probability is not high.** RESEARCH.md estimates < 50%. The underlying issue is the canned-suffix generation pipeline in `scripts/gen_tool_calls.py`, which needs real structural change — not just a pool expansion. A naïve pool expansion can still collapse onto the new modes if the generator's structural templates are too narrow.
- v3 could fail D-09 on either axis: format might not reach 0.41 OR knowledge might still be >5% below base.
- MMLU recovery depends on whether the skew reduction is aggressive enough; at 0.80 tool-calling (20% code+knowledge) gradient coverage is still low.

**Wall-clock estimate:** ~1 h data rework (pipeline change + re-curation + re-assembly) + ~3.5 h training + ~1 h eval = ~5.5 h. If v3 fails and a v4 is authorized per D-10, add another ~5 h. Hard ceiling before fall-back to 06C should be 2 retrain attempts (~10–11 h total).

### Branch 06B — Targeted patch (NOT SELECTED)

**When this would be the right choice:** Evidence points at a single-point bug (e.g., a post-processing step that strips `<tool_call>` from assistant outputs, or a tokenizer-level transformation that corrupts XML). Requires citing a specific file + line + transformation that, if fixed, would recover ≥ 0.20 tool-call-format *without* any retrain.

**Why it is NOT the right choice here:**
- The evidence does not point at a localized bug. It points at distribution. You cannot patch around "0.00% of training samples end in a tool_call" — the model was never shown what to do.
- D-04 already ruled out template bugs (the one class of single-point fix with highest prior).
- D-05 shows the mode collapse is about WHICH tool + WHICH args, not about XML format emission. A post-processing patch cannot rewrite `get_weather(city="Tokyo")` into `get_time(city="Tokyo")` based on the user prompt — that requires the model to have learned the right semantic mapping, which it hasn't.
- The only "targeted patch" that would move the metric is an eval-side patch that either (a) adds single-turn samples to the test set (scope expansion the user has explicitly said is out of scope — RESEARCH.md Open Question 3 RESOLVED), or (b) changes `check_tool_call_format` scoring logic (makes comparisons with Phase 9 incomparable).

**Use only if:** user surfaces a specific single-point fix not considered here, with evidence citation. Otherwise skip.

## Rationale for the 06A Recommendation

1. **H1 is the confirmed root cause (posterior ~90%), and 06A is the only branch that directly addresses it.** Per D-06 (Plan 04), the problem is measurable on disk: 0.00% tool-call-ending train samples, 46.0% top-5 suffix coverage, 90.22% domain skew. Per D-03/D-05 (Plan 03), the behavioral signature at inference exactly matches those three numbers' predictions. A retrain with the three data-distribution fixes is the only operation that can actually move those numbers, and therefore the only operation that can actually lift v3 toward the D-09 bar.
2. **06B is not applicable given the evidence.** Per D-03 + D-05 categorization, the regression is about distribution and semantic selection, not a localized transformation. No single file + line + transformation exists whose fix would recover ≥ 0.20 tool-call-format without retraining. 06B requires evidence it does not have.
3. **06C has a hidden D-09 problem that 06A might avoid.** Per D-07 (amended), the base model's tool-call-format against the *current* test split is 0.3422, not 0.4065. 06C therefore does not satisfy D-09 as literally written; it would require either renegotiating the bar, changing the measurement split, or explicitly accepting a D-09 miss under D-02. These are all reasonable decisions the user can make, but they should be made consciously — 06C is not a "free pass" to D-09 success.
4. **The recommendation is 06A *with* 06C as a pre-committed fall-back.** Per D-10, retrain attempts are not capped but each must cite a changed hypothesis. If v3 fails D-09, Plan 05 re-synthesizes with the new evidence and the user decides v4 (with a new hypothesis) vs. 06C. This bounds the retrain cost at 1–2 attempts (~5–11 h) before the fall-back is mandatory.
5. **06A is the only path that produces a Lyra-branded artifact above the D-09 bar.** Given the investment in the fine-tuning pipeline, the dataset generation infrastructure, and the training stack, a successful 06A retrain is the outcome that actually fulfills Lyra's v1.0 mission statement. 06C is a retreat that the user should only choose if 06A has been tried and failed.
