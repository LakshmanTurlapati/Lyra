# Phase 09.2: Tool-Call Regression Diagnosis - Research

**Researched:** 2026-04-23
**Domain:** LLM eval diagnostics, LoRA fine-tune failure modes, chat-template parity, dataset-skew pathologies
**Confidence:** HIGH (empirically verified against the v2 merged model and assembled dataset during this research session)

## Summary

The 09.1 retrain did not fail because of a chat-template bug. During this research session I empirically verified five things against the on-disk v2 model and dataset:

1. The train-time and persisted templates are **bit-identical** after `{% generation %}` marker stripping (733 → 698 chars; persisted matches stripped train template exactly).
2. When both templates render the same normalized eval prompt, they produce **identical token IDs** across 5 consecutive tool-calling test samples (zero mismatches).
3. On `[system, user]` single-turn tool-call prompts, v2 **can** emit the `<tool_call>[...]</tool_call>` XML format — but it collapses onto `get_weather(city=Tokyo)` for every prompt regardless of content (5/5 probes returned a Tokyo weather call, including for "Search for AI news" and "What time is it in Tokyo?").
4. On multi-turn "summarize-after-tool-result" prompts — which make up **562 of 599 (94%)** tool-calling test samples — v2 **echoes the tool-result turn verbatim** as its assistant response in roughly 8/20 hand-inspected cases and produces bland plain-text summaries in 9/20.
5. The training set has a catastrophic label-distribution mismatch with the test set: 100% of the 10,793 train tool-calling samples end in an **assistant text summary** (not a tool call), and over 5,000 of those summaries are near-duplicates of five canned templates ("I've gathered all the information...", "I've completed the task...", "The results show...", "Based on the results..."). Combined with the 90.2% tool-calling domain skew, the model has been optimized to regurgitate these templates.

The regression is real, the 0.0634 number is real, and the eval methodology (measuring `<tool_call>` format emission on a test set that expects text) is indeed quirky — but v2 is objectively worse than the base model in every meaningful way: worse on format emission, worse on prompt variety, worse on MMLU (-7.5%). The base model scored 0.4065 by **correctly** emitting tool-calls for the 37 single-turn test prompts AND **incorrectly hallucinating** tool-calls for ~20-25% of the summarize-after-result prompts; v2 lost both of those axes.

**Primary recommendation:** Do NOT retrain before rebalancing the training set. The single fastest-to-ship path to the D-09 exit bar is to **revert to the Phase 9 checkpoint** — the Phase 9 Lyra scored 0.1870 on tool-call-format (below the 0.41 bar) and was itself below the base model. Neither Lyra snapshot beats the base. The exit criterion is `tool-call-format > 0.41`; only the base model satisfies it. The cleanest exit is to ship the base model with a documented explanation (or a cheap eval-methodology fix that makes the metric more meaningful, if user permits scope). A retrain could work but it requires D-04-evidence-backed fixes to the training distribution, not template mechanics.

### Pattern 1: Template Parity Pytest (D-04 validation)

**What:** Prove that train-time template (stripped of `{% generation %}`) and persisted template produce bit-identical token IDs on a fixture prompt. Make this a pytest so future train.py changes can't silently break parity again.

**When to use:** Once. Keep the test permanently.

**Example:**
```python
# Source: VERIFIED empirically this research session — 5/5 samples matched
# tests/test_template_parity.py
import json
from pathlib import Path
import pytest

TRAIN_TEMPLATE = (
    "{% for message in messages %}"
    "{% if loop.first and messages[0]['role'] != 'system' %}"
    "{{ '<|im_start|>system\nYou are a helpful AI assistant named SmolLM, trained by Hugging Face<|im_end|>\n' }}"
    "{% endif %}"
    "{% set msg_content = message['content'] if message.get('content') else '' %}"
    "{% if message.get('tool_calls') %}"
    "{% set msg_content = '<tool_call>' + message['tool_calls']|tojson + '</tool_call>' %}"
    "{% endif %}"
    "{% if message['role'] == 'assistant' %}"
    "{% generation %}"
    "{{ '<|im_start|>' + message['role'] + '\n' + msg_content + '<|im_end|>\n' }}"
    "{% endgeneration %}"
    "{% else %}"
    "{{ '<|im_start|>' + message['role'] + '\n' + msg_content + '<|im_end|>\n' }}"
    "{% endif %}"
    "{% endfor %}"
    "{% if add_generation_prompt %}"
    "{{ '<|im_start|>assistant\n' }}"
    "{% endif %}"
)

@pytest.mark.slow  # depends on tokenizer download
def test_train_and_persisted_templates_produce_identical_tokens():
    from transformers import AutoTokenizer
    tok = AutoTokenizer.from_pretrained("models/lyra-merged")
    persisted = tok.chat_template

    # Strip generation markers from TRAIN_TEMPLATE and assert string equality
    inference_train = TRAIN_TEMPLATE
    for marker in ["{% generation %}", "{% endgeneration %}"]:
        inference_train = inference_train.replace(marker, "")
    assert inference_train == persisted, "Template persistence regression"

    # Fixture prompt (single-turn tool-call with system prompt)
    msgs = [
        {"role": "system", "content": "You are a test assistant."},
        {"role": "user",   "content": "What's the weather in Paris?"},
    ]

    tok.chat_template = TRAIN_TEMPLATE
    ids_train = tok(tok.apply_chat_template(msgs, tokenize=False, add_generation_prompt=True))["input_ids"]
    tok.chat_template = persisted
    ids_pers  = tok(tok.apply_chat_template(msgs, tokenize=False, add_generation_prompt=True))["input_ids"]
    assert ids_train == ids_pers, f"token-ID drift: first diff at {next((i for i,(a,b) in enumerate(zip(ids_train,ids_pers)) if a!=b), 'EOF')}"
```

### Pattern 2: Probe Script Skeleton (D-03 + D-05)

**What:** Standalone script that loads v2, runs N prompts, writes raw generations to `results/*.jsonl` with a category tag. Covers BOTH D-03 (categorize 20+ real test-set failures) and D-05 (5–10 hand-picked single-turn probes).

**When to use:** One-off. Commit the script but delete generated artifacts.

**Example:**
```python
# Source: VERIFIED on actual v2 model during research — script produced categorization
#   revealing "echo_tool_result_prefix" (8/20) and mode collapse onto weather(Tokyo)
# scripts/probe_generations.py
import argparse, json, os, re, sys
from pathlib import Path

os.environ.setdefault("PYTORCH_ENABLE_MPS_FALLBACK", "1")

def categorize(generated: str, expected_content: str) -> str:
    m = re.search(r"<tool_call>(.*?)</tool_call>", generated, re.DOTALL)
    if m:
        try:
            json.loads(m.group(1))
            return "valid_tool_call"
        except json.JSONDecodeError:
            return "malformed_tool_call_json"
    if not generated.strip():
        return "empty"
    if generated.lstrip().startswith("[Tool result from"):
        return "echo_tool_result_prefix"
    if expected_content and expected_content[:30] in generated:
        return "echoed_expected_text"
    if "<tool_call>" in generated:
        return "incomplete_tool_call"
    return "plain_text"

def normalize_messages(msgs):  # MUST mirror eval_inference._normalize_messages_for_template
    out = []
    for m in msgs:
        r = m.get("role", ""); c = m.get("content", "")
        if r == "assistant" and not c and m.get("tool_calls"):
            out.append({"role": "assistant",
                        "content": f"<tool_call>{json.dumps(m['tool_calls'])}</tool_call>"})
        elif r == "tool":
            tn = m.get("name", "tool")
            out.append({"role": "user", "content": f"[Tool result from {tn}]: {c or ''}"})
        else:
            out.append({"role": r, "content": c})
    return out

def main():
    p = argparse.ArgumentParser()
    p.add_argument("--model", required=True)
    p.add_argument("--mode", choices=["dataset", "single-turn"], required=True)
    p.add_argument("--limit", type=int, default=20)
    p.add_argument("--dataset-dir", default="datasets/assembled")
    p.add_argument("--output", required=True)
    p.add_argument("--max-new-tokens", type=int, default=256)
    args = p.parse_args()

    import torch
    from transformers import AutoTokenizer, AutoModelForCausalLM
    tok = AutoTokenizer.from_pretrained(args.model)
    model = AutoModelForCausalLM.from_pretrained(args.model, torch_dtype=torch.float32).to("mps")

    out_rows = []
    if args.mode == "dataset":
        from datasets import load_from_disk
        ds = load_from_disk(args.dataset_dir)
        count = 0
        for i, s in enumerate(ds["test"]):
            if s.get("domain") != "tool-calling":
                continue
            count += 1
            if count > args.limit:
                break
            msgs = s["messages"]
            last = max(j for j, m in enumerate(msgs) if m["role"] == "assistant")
            prompt_msgs = normalize_messages(msgs[:last])
            expected = msgs[last]
            prompt = tok.apply_chat_template(prompt_msgs, tokenize=False, add_generation_prompt=True)
            inputs = tok(prompt, return_tensors="pt").to("mps")
            with torch.no_grad():
                o = model.generate(**inputs, max_new_tokens=args.max_new_tokens,
                                   do_sample=False, pad_token_id=tok.pad_token_id)
            gen = tok.decode(o[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True)
            out_rows.append({
                "idx": i,
                "expected_content": expected.get("content", "")[:200],
                "expected_has_tool_calls": bool(expected.get("tool_calls")),
                "generated": gen,
                "category": categorize(gen, expected.get("content", "")),
            })
    else:
        PROBES = [
            "What's the weather in New York?",
            "What time is it in Tokyo?",
            "Search for the latest news about AI.",
            "Call get_weather for London.",
            "I need the current temperature in Paris. Use the weather tool.",
            "Run `ls -la` in the current directory.",
            "Commit my changes with message 'fix regression'.",
            "Read the contents of /etc/hosts.",
        ]
        sys_prompt = ("You are a helpful AI assistant with access to tools. When a tool is needed, "
                      "respond with <tool_call>[{...}]</tool_call>. Available tools: "
                      "get_weather(location), get_time(location), search_web(query), "
                      "run_command(cmd), git_commit(message), read_file(path).")
        for p_text in PROBES:
            msgs = [{"role": "system", "content": sys_prompt},
                    {"role": "user", "content": p_text}]
            prompt = tok.apply_chat_template(msgs, tokenize=False, add_generation_prompt=True)
            inputs = tok(prompt, return_tensors="pt").to("mps")
            with torch.no_grad():
                o = model.generate(**inputs, max_new_tokens=args.max_new_tokens,
                                   do_sample=False, pad_token_id=tok.pad_token_id)
            gen = tok.decode(o[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True)
            out_rows.append({"user": p_text, "generated": gen,
                             "category": categorize(gen, "")})

    Path(args.output).parent.mkdir(parents=True, exist_ok=True)
    with open(args.output, "w") as f:
        for row in out_rows:
            f.write(json.dumps(row) + "\n")

    # Print category histogram for quick review
    from collections import Counter
    cats = Counter(r["category"] for r in out_rows)
    print("=== Category histogram ===")
    for c, n in cats.most_common():
        print(f"  {c:30s} {n}")
    return 0

if __name__ == "__main__":
    sys.exit(main())
```

### Pattern 3: Safe Generation Defaults for Diagnosis

**What:** Generation kwargs that isolate "can the model produce this format?" from "is my sampling hiding the failure?"

| Kwarg | Safe value | Why |
|-------|-----------|-----|
| `do_sample` | `False` (greedy) | Deterministic; matches `eval_inference.py` line 233 — reproducibility across runs |
| `max_new_tokens` | `256` | Matches eval_inference default; enough for a `<tool_call>...</tool_call>` + short follow-up |
| `temperature` | (unused with greedy) | Don't set with `do_sample=False`; transformers emits a warning |
| `repetition_penalty` | **do NOT set** | Would mask the echo-tool-result-prefix failure mode, which is the smoking gun |
| `pad_token_id` | `tok.pad_token_id` | Required on MPS to suppress a warning; does not affect output semantics |
| `torch_dtype` | `torch.float32` on MPS | bf16/fp16 numerics differ on MPS and can hide or introduce failure modes. [CITED: Phase 9 used float32 on MPS throughout] |

**Do not vary these during diagnosis.** If a retrain is authorized, separately validate each deviation.

### Anti-Patterns to Avoid

- **Running D-04 template diff in isolation and declaring victory.** A bit-identical template + identical token IDs is necessary but NOT sufficient — I verified both during this session, and the model is still broken.
- **Inferring root cause from loss curves alone.** eval_loss 0.1384 is suspiciously low in hindsight, but by itself does not tell you whether the model memorized canned summaries or learned real capability. Only raw-generation inspection resolves this.
- **Retraining with changed hyperparams before fixing data distribution.** Lowering LR or dropping epochs on a 90.2%-skewed dataset with 5 canned summary templates will yield a slightly-less-collapsed model that still fails D-09.
- **Attempting to "fix" the eval metric to make v2 pass.** The eval is flawed (all 599 test labels are text, not tool calls) but v2 is ALSO worse on qualitative inspection — the base model answers "what time is it in Tokyo" with a tool_call; v2 answers "what time in Tokyo" with `get_weather(Tokyo)`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Chat template rendering in the probe | Manual f-string prompt construction | `tokenizer.apply_chat_template()` | Must match eval_inference exactly; any drift is a new confound |
| Message normalization (tool → user) | New helper in the probe | Import `_normalize_messages_for_template` from `scripts.eval_inference` | Mirrors the eval path precisely; eliminates normalization drift |
| Token-ID comparison | Custom `str(ids)` compare | `list(ids) == list(ids)` on the Python lists | Tokenizer `input_ids` are plain Python lists when `return_tensors=None`; direct equality is correct |
| Re-baseline of base model | "Trust the old file" | Re-run `eval_inference.py` + `eval_runner.py --limit 100` and diff against prior results | The whole point of D-07 is to detect eval-pipeline drift since Phase 9 |

## Common Pitfalls

### Pitfall 1: Treating template-parity proof as sufficient
**What goes wrong:** You verify D-04 produces zero token diffs and declare the model must be fine. The model is still broken — template is a necessary but not sufficient condition.
**Why it happens:** Phase 09.1 research already made this mistake in reverse (declared template was broken when it wasn't). Now the temptation is to swing the other way.
**How to avoid:** Always run D-04 AND D-03 AND D-05 before forming a root-cause hypothesis. One data source cannot adjudicate.
**Warning signs:** Sentence in a plan that says "Since the template is correct, the issue must be in {X}" without triangulating evidence.

### Pitfall 2: Measuring failure on the test set that was designed for a different task
**What goes wrong:** `check_tool_call_format` measures "output contains valid `<tool_call>...</tool_call>` XML." But 562 of 599 test labels are *text summaries* — so the metric rewards hallucinating tool-calls. Lower score can mean "less confused" OR "worse capability"; you can't tell from the metric alone.
**Why it happens:** `datasets/assembled/test` was stratified at 90.2% tool-calling, but all tool-calling test samples preserve the multi-turn structure ending in a text turn (matching training). The custom eval was written assuming tool-calls were sometimes the label.
**How to avoid:** Planner has discretion (per CONTEXT.md) to add single-turn test samples where a tool-call IS the expected output. The D-05 probe verifies this can even be measured before authorizing a retrain.
**Warning signs:** Eval score "improves" after retrain but the D-05 probe still shows mode collapse.

### Pitfall 3: Overfitting on canned summary templates
**What goes wrong:** 90.2% of training samples are tool-calling multi-turn, and 100% of those end with one of five near-duplicate phrases ("I've gathered all the information...", "I've completed the task...", etc.). eval_loss 0.1384 reflects memorization of these fixed suffixes, not real capability.
**Why it happens:** Template-based generation with a finite pool + full-scope dedup at 0.9 threshold removes near-duplicates *between* conversations but not the canned endings *within* each conversation.
**How to avoid:** If retraining is authorized, either (a) rewrite `scripts/gen_tool_calls.py` to sample from a vastly expanded ending pool, (b) oversample the 649 code + 651 knowledge samples to reduce the 90.2% skew (WeightedRandomSampler or manual `dataset.repeat()`), or (c) drop the summarize-after-result category from training and rely on the base model's text ability for those.
**Warning signs:** Top-N frequency counts on `msgs[-1]["content"]` show >30% of training samples share the same 60-character prefix. (We just measured this; it's 46% / 5000 of 10,793 train tool-calling samples.)

### Pitfall 4: Assuming low eval_loss ⇒ good model
**What goes wrong:** Epoch 1: 0.1613, Epoch 2: 0.1384 — monotonically decreasing and very low. Looks like a clean training run. But validation loss is computed on the SAME distribution as training (90.2% tool-calling, 5 canned endings). A model that memorizes those endings gets low validation loss AND fails in the wild.
**Why it happens:** The assembled dataset's validation split (666 samples, 90.2% tool-calling) mirrors train's distribution. There is no out-of-distribution held-out check.
**How to avoid:** Add a small "probe" eval set to the training loop — 20 hand-written single-turn prompts outside the template pool — and report its pass-rate every epoch. Not scope for this phase, but a note for a future phase.
**Warning signs:** eval_loss decreases while single-turn probe outputs degenerate. This is exactly what happened for v2.

### Pitfall 5: MPS fp16/bf16 silent numerics drift
**What goes wrong:** Merge step in `train.py` line 508 loads the base model in `torch.float16` for the merge: `AutoModelForCausalLM.from_pretrained(args.model_name, torch_dtype=torch.float16)`. The adapter was trained in fp32 (MPS default, no bitsandbytes). Merging fp32 LoRA into fp16 base involves a cast that on MPS may differ from CUDA. [ASSUMED — not tested this session; risk level LOW because base weights are already fp16 on HF Hub]
**Why it happens:** MPS has known silent-correctness bugs when operations fall back via `PYTORCH_ENABLE_MPS_FALLBACK=1` (especially Conv1d, view operators). [CITED: pytorch/pytorch#134416, pytorch/pytorch#86195]
**How to avoid:** If retrain is authorized and fresh-probe still shows degradation, re-run the merge step with `torch.float32` base loading and compare merged weights bitwise.
**Warning signs:** `diff_templates.py` passes but single-turn probe still degenerates. Then suspect merge-time numerics.

### Pitfall 6: Revert confusion (D-08 trap)
**What goes wrong:** Plan says "revert to Phase 9 checkpoint," but D-08 states the pre-09.1 Lyra merged model was overwritten in Plan 05's merge step. The *only* pre-09.1 artifact on disk is what git LFS is currently tracking — which is now v2.
**Why it happens:** "Checkpoint" is ambiguous — adapter-only state, merged state, git tag, or conceptual "last known good score."
**How to avoid:** Be explicit. "Revert" means: (a) `git log --all -- models/lyra-merged/model.safetensors` to find the SHA before Plan 05's merge commit, (b) if that SHA's LFS blob is still pullable (`git lfs fetch origin <sha>`), check it out; otherwise (c) accept D-08 and ship the base model.
**Warning signs:** Plan task says "checkout previous model" without specifying a git SHA or LFS blob identity.

## Ranked Hypothesis List

Given the evidence — 0.0634 format score (-0.34 vs base), 0.1384 eval_loss, 90.2% tool-calling skew, 46% of training tool-calling samples sharing 5 ending phrases, v2 emits tool_call on single-turn but collapses onto `get_weather(Tokyo)`, v2 echoes the tool-result verbatim on summarize-after-result prompts — here are the hypotheses ordered by likelihood:

### H1 (HIGHEST — ~70% probability): Training-data mode collapse onto canned suffix templates + domain skew
**Evidence:**
- 10,793/10,793 train tool-calling samples end with assistant TEXT (never tool_call) — this is the 100% I measured this session
- Top 5 ending prefixes cover ~46% of those ~10K samples ("I've gathered...", "I've completed...", "The results show...", "Based on...", "Here's what I found...")
- 90.2% of training is tool-calling; 4.9% code, 4.9% knowledge
- v2 generation behavior on summarize-after-result prompts: exact-echo of the prior tool result (8/20) or exact-echo of canned summary (2/20) — i.e., attention to the final template token dominates
- eval_loss 0.1384 is consistent with memorizing 5 suffix templates (low entropy to optimize against)

**Why it explains all observations:**
- Mode collapse on single-turn: the model learned the *suffix distribution* of tool-call turns better than the *content* of user queries, so `get_weather(Tokyo)` is simply the most frequent (`Tokyo` appears 134 times, `get_weather` is implicit in the tool-call pool) modal tool-call in training
- Echo-tool-result-prefix: the canned `"[Tool result from {name}]: {content}"` injection on the user side of training is being re-emitted by the assistant because the assistant is near-duplicating canned phrases
- MMLU -7.5%: catastrophic forgetting on general knowledge, classic skew symptom

**Corrective action:** Retrain with (a) rebalanced domain ratios (WeightedRandomSampler pushing code/knowledge to ~25-30% each), (b) expanded ending-phrase pool in `scripts/gen_tool_calls.py`, (c) lower LR (5e-5) to reduce overfitting to the remaining skew. Do NOT retrain without (a) AND (b). Plan must include a data-audit task before retrain.

### H2 (MEDIUM — ~15%): assistant_only_loss + generation-marker interaction is masking the wrong tokens
**Evidence:**
- `assistant_only_loss=True` in `get_training_args` (train.py line 356)
- `{% generation %}` / `{% endgeneration %}` markers wrap the entire assistant turn, including any `<tool_call>...</tool_call>` content
- [CITED: Context7 /huggingface/trl confirms markers are REQUIRED for `return_assistant_tokens_mask=True` to produce accurate masks]

**Why it might explain:**
- If TRL's mask-computation skips `<tool_call>` tokens for some reason (e.g., they span across structural tokens), the model trains on `<|im_start|>assistant\n...<|im_end|>` boundaries but not on the XML contents themselves

**Why it's probably not the whole story:**
- Phase 8 used the same markers and Phase 9 Lyra scored 0.187 (not great, but 3× better than v2)
- Token-ID parity (D-04) is bit-exact, which means the SAME token stream is being fed; the loss mask is computed from the same tokens

**Corrective action (if H2 is supported):** Dump the assistant-token mask via TRL's debug hooks on a training sample; visually confirm `<tool_call>` tokens are in the mask.

### H3 (MEDIUM — ~10%): Eval methodology artifact, not a real capability regression
**Evidence:**
- 562/599 (94%) tool-calling test samples have TEXT as the expected label, not tool_calls
- `check_tool_call_format` rewards ANY `<tool_call>` emission, even hallucinated ones
