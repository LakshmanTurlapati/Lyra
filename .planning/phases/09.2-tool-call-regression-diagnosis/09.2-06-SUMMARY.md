### Blocker 1 — Task 0 dispatch regex matches both 06A and 06C

The dispatch regex at 09.2-06-PLAN.md Task 0 (`(?i)(approved?:?\s*06X|\bapprove 06X\b|\[x\].*06X)`) is too loose: it matches on any `[x] ... 06C` line, including the reviewer-acknowledgement line `[x] User reviewed the three-branch analysis and D-09-against-current-split caveat in 06C` and the approval line `[x] User approves the chosen action (circle one): **06A** — with **06C as pre-committed fallback**`. Running the script as written exits code 2 with `SELECTED=['06A', '06C']`.

The orchestrator prompt unambiguously specifies **06A only** (06C reserved as a second-dispatch fallback if v3 fails D-09). This is not a branch-ambiguity problem at the approval layer — the approval is clear — it is a regex-precision problem at the dispatch layer.

**Proposed fix (Rule 3-class, small):** Task 0 regex should require the approval marker on its own line without the word "fallback" nearby, e.g. `r"(?im)^.*\[x\].*\bApproved?:?\s*\*\*06[ABC]\*\*"` or adopt an explicit approval line in DIAGNOSIS.md ("Approved: 06A" on its own line). Current fix requires either (a) patching the dispatch regex in 09.2-06-PLAN.md, or (b) adding an unambiguous `Approved: 06A` line to DIAGNOSIS.md.

### Blocker 2 — Task A1 hyperparameter parsing fails

Task A1 pre-flight requires DIAGNOSIS.md to contain `lr: <value>` and `epochs: <value>` lines in a form grep-parsable via `^lr:[[:space:]]` / `^epochs:[[:space:]]`. DIAGNOSIS.md 09.2-DIAGNOSIS.md lines 90-91 have the values but inside Markdown bullet prose:

```

  - `epochs`: 2 → 1 (epoch-2 eval_loss dropped 0.0229 which was mostly deepening the memorization; 1 epoch limits that)
```

Running the plan's pre-flight script:
```
LR=$(grep -E '^lr:[[:space:]]' "$DIAGNOSIS" | head -n1 | awk '{print $2}')
EPOCHS=$(grep -E '^epochs:[[:space:]]' "$DIAGNOSIS" | head -n1 | awk '{print $2}')
```
returns empty strings, and the subsequent `python3 -c "... float(lr_s); int(ep_s)"` fails with `STOP: fix DIAGNOSIS.md Branch 06A section (add lines: lr: <value> and epochs: <value>) then re-run`.

Per the plan's own explicit pre-flight language: "Do NOT default-pick values. If DIAGNOSIS.md is vague, STOP and re-prompt the user." The values are clearly intended (`lr=5e-5`, `epochs=1`), but the plan deliberately demands they be in an unambiguous machine-readable form before any 3.5 h training cycle burns compute on the wrong hyperparameters.

**Proposed fix (Rule 3-class, trivial):** Add two lines to DIAGNOSIS.md Branch 06A section (or a new "Hyperparameters" sub-section):
